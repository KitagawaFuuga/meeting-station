# 合流駅さがし（仮称）設計

2026-10-25。fare-map を流用して作る新しいアプリの設計。

## 1. 何のためか

二人が別々の駅から同じ目的駅へ電車で向かうとき、途中で落ち合って一緒に行ける駅を探す。
目的駅で直接待ち合わせるより、道中で合流して一緒に移動したい、というのが出発点（ユーザーの言葉）。

例: A さんは大宮から、B さんは立川から、横浜へ。二人の経路が新宿で重なるなら新宿で落ち合う。
少し遠回りしてでも早めに落ち合うか、遠回りを避けて目的駅の近くで落ち合うかは、そのときどきで変わる。
なので、どちらを優先するかは画面で切り替えられるようにする。

## 2. ゴール・ゴールでないもの

ゴール
- 3駅（A の出発駅・B の出発駅・目的駅）を入れると、合流駅の候補が地図と表で出る
- 候補ごとに「A の遠回り」「B の遠回り」「一緒に乗る区間」が数字でわかる
- 物差し（料金／距離）と並べ方（遠回りが少ない順／長く一緒に乗れる順）を切り替えられる

ゴールでないもの（今回はやらない）
- 所要時間での比較。所要時間のデータ集めとライセンス確認が済んでから追加する（fare-map の docs/reuse-guide.md 5章のとおり、ODPT は都営以外は再配布禁止）
- 3人以上の合流
- 遠回りの上限を入れて候補を絞り込む機能。候補は絞り込まずに全部出して、並べ方で選ぶ（ユーザーの選択）
- 乗換案内（何時の電車に乗るか）

避けたい結果: ユーザーは「完成品を見てから考える」と言っている。なので、最初の版は早く動くものを出すことを優先する。

## 3. 決まっていること

### 画面（ユーザーが画面案を見て選んだもの）

- 結果は**地図と比較表の両方**を出す
- 表の1行が合流駅の候補1つ。列は「合流駅」「A の遠回り」「B の遠回り」「一緒に乗る区間」
- 切り替えは2つ
  - 物差し: 料金 ／ 距離
  - 並べ方: 遠回りが少ない順 ／ 長く一緒に乗れる順
- 候補は全部出す（上限で絞り込む案は採らなかった）

### 私の案としてユーザーが了承したもの

- 入力欄は fare-map と同じく文の形にする。「〇〇 と △△ から □□ へ」
- 表の行を選ぶと、地図にその候補での二人の経路と合流駅の印を出す
- スマホでは、fare-map と同じく地図の上にボトムシートで表を出す
- 「遠回りが少ない順」は二人の遠回りの合計で並べる。合計が同じなら、二人の差が小さいほうを上にする（片方だけが損をする候補を下げる）
- 候補にするのは、合流してから目的駅まで一緒に乗る区間が残る駅。目的駅そのものは「現地集合」として最後の候補に含める
- 人数は二人に固定する

### 作り方

- fare-map とは**別の新しいリポジトリ**として作り、別のアプリとして公開する
- 範囲は fare-map と同じく全国
- 技術構成・公開方法・CI は fare-map と同じ（docs/reuse-guide.md 1章・3章）。Next.js 16 / TypeScript strict / MapLibre + OpenFreeMap / Vitest / Playwright / Azure Container Apps / Docker Hub / GitHub Actions
- TDD を Probity で強制する設定も持っていく
- 流用する部品は docs/reuse-guide.md 2章の表。データ（`data/` の路線グラフ・運賃規則一式）と生成スクリプトもそのまま持っていく。持っていき方はコピー（submodule やパッケージにはしない。私の判断）
- reuse-guide.md 7章の既知の課題（レート制限の IP の取り方など）は、持っていく前に直す

## 4. 遠回りの定義

ある駅 M で合流するとき、A の遠回りは

> A の遠回り ＝ （A→M の量）＋（M→目的駅 の量）−（A→目的駅 の量）

B も同様。「量」は物差しが距離なら営業キロ、料金なら運賃。
一緒に乗る区間は M→目的駅 の量（並べ方「長く一緒に乗れる順」はこれの大きい順）。

距離は足し算で成り立つので、二人の最短経路上にある駅は遠回り 0 になる。

### 料金は「M を通る通しの運賃」で数える（ユーザーの決定）

改札を出ずに乗り続ければ、M で落ち合っても追加料金はかからない。この実態に合わせるため、料金の遠回りは次のように定義する。

> A の遠回り ＝ （A から M を通って目的駅まで、通しで乗ったときの最安運賃）−（A から目的駅までの最安運賃）

M で切符を分けて計算する方式（実装は簡単）は採らない。
fare-map の探索（`lib/search/reachable.ts`）は1つの出発駅から全駅への運賃を出すだけで、「M を必ず通る」制約は持っていない。なので探索を拡張する必要がある。
たとえば状態に「M を通過済みか」を足す、M ごとに制約つきの探索を走らせる、など。作り方は作る人に任せる。
候補の母集団（下記）で M の数が絞られることを前提にしてよい。
同じ料金なら距離が短い経路を選ぶ。遠回りが負になったら 0 として扱う（私の判断）。

### 候補の母集団（ユーザーの決定）

A・B それぞれの遠回りが、その人が目的駅まで直接行く量の**半分以内**に収まる駅だけを候補にする。
- 例: 大宮→横浜が約 50km なら、A の遠回りは 25km まで
- 物差しが料金のときは運賃で判定し、距離のときは距離で判定する（私の判断）
- この上限は固定値。利用者が入力するものではない（2章の「上限で絞り込む機能は作らない」とは別物）
- 理由: 上限がないと、「長く一緒に乗れる順」の上位に、片方の背後の駅（大宮より先の宇都宮など）が並んでしまう

### 経路と距離の出どころ（私の判断）

- 距離の物差しでは、営業キロが最短の経路を使う。fare-map の探索は `{id, fare}` しか返さないので、営業キロの最短経路を返す探索（経路の復元つき）を新しく書く
- 料金の物差しでは、上の通し運賃が最安になる経路を使う
- 地図に描く経路は、選んだ物差しでの「A→M」「B→M」「M→目的駅」の3区間

### 並べ方の細部（私の判断）

- 「遠回りが少ない順」: 二人の遠回りの合計の小さい順。同じなら二人の差の小さい順、それでも同じなら一緒に乗る区間の長い順
- 「長く一緒に乗れる順」: M→目的駅 の量の大きい順。同じなら遠回りの合計の小さい順
- 目的駅（現地集合）は、どちらの並べ方でも常に最後に置く

### 性能（私の判断）

- 目標は 1 回の問い合わせで 2 秒以内（本番の 0.5 vCPU で測る）
- 目的駅を起点にした探索は、目的駅ごとに fare-map の `result-cache` でキャッシュする

## 5. 作る人に任せること

- アプリ名・リポジトリ名・Azure のリソース名
- API の形（1回の問い合わせで候補一覧と経路を返すか、経路は行を選んだときに別に取るか）
- 地図上で二人の経路をどう描き分けるか（色・線の太さ）。fare-map の色の考え方（reuse-guide.md 2章「考え方だけ持っていくもの」）に合わせる
- 候補が多すぎるときに表を何件まで出すか、地図に印を何件まで出すか
- 同じ駅の別路線（groupId が同じノード）をまとめて1候補にするやり方
- 出発駅と目的駅が同じ、二人の出発駅が同じ、などの端の入力の扱い
